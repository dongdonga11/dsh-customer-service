# AGENTS.md 与知识库「规则层」设计（需求梳理稿）

> 状态：**只梳理、不动工**（运营者要求先对齐需求）。
> 目标：让客服 AI 像真正的 harness 工程一样有**明确范围边界、数据源登记、工具调用规则、沉淀与更新机制**；
> 店规只是「事实资料」的一部分，话术沉淀是「把经验变成规则」的机制，产品 Excel 是「结构化资料」的一种。

---

## 1. 你的需求（我理解的）

1. 每个客服项目要有一份类似 `AGENTS.md` 的**项目规则文档**：说清 AI 是谁、能答什么、不能答什么、什么场景读哪份资料、什么场景调什么工具/MCP、什么情况必须转人工。
2. 这份规则要**可以更新**：以后新增资料（店规、话术、产品表、图片）时，除了放文件，还要在规则里登记「它是什么、什么时候用、优先级」。
3. 现有的**店规**其实已经很接近这种「规则+事实」混合体，可以拆成：规则层（怎么答）+ 事实层（答什么）。
4. **话术沉淀**：从真实对话里复盘出可复用的问答/打法，评审后并入知识库，并在规则变更记录里留痕。
5. **产品 Excel 表**：需要让 AI 能查（型号/价格/卖点/库存口径），并明确「以哪个为准、成本价之类敏感列不能给买家」。
6. **图片**：新增了图片素材后，要能声明「什么时候发哪张图」（地址图、效果图、新品图），以及 AI 能不能自动发。
7. 最终效果：AI 的回答不是靠运气检索，而是「规则先定边界，资料给事实，工具补实时」。

## 3. 分层模型（建议）

```
L0 硬约束（代码级，任何文档都不能绕过）
   · AI 默认关闭；只有明确开启才自动回
   · 退款/赔付/免单/承诺时间/保证店铺 → 一律转人工
   · 不可逆平台操作（关闭订单/退款/改价/发品）→ 必须人工确认
   · 发送前复查（人工刚回过就让位）、审计全量留痕

L1 项目 AGENTS.md（规则层，每个项目一份，进 AI 上下文最前面）
   · 身份/语气/输出格式
   · 范围边界：可答 / 不可答 / 必转人工
   · 数据源登记表：文件、类型、优先级、什么时候读
   · 工具 & MCP 调用策略表：场景 → 动作 → 前置条件 → 确认要求 → 失败兜底
   · 图片/素材使用规则
   · 升级与交接规则
   · 变更记录（版本/日期/改了什么/为什么）
   · 自测问句（验收样例：问句 → 期望行为）

L2 事实资料（检索层，AI 按需读）
   · 店规细则（规则全文/FAQ）
   · 话术库（按意图分类：接待/价格/催发货/售后/新品）
   · 产品表（Excel 导入后的结构化资料）
   · 图片素材 + 素材清单
   · FAQ / 历史优质对话

> 账号未绑定任何项目时：适配器返回「该账号还没分配项目」，**不再退回旧 `客服知识库`**（旧路径已不存在，退回只会报 ENOENT 误导）；
> 面板把这种情况显示为灰色提示（不是红色故障），只有项目资料/规则真的坏了才告警。

## 3.1 原则（2026-10-20 修正，务必遵守）

- **AGENTS.md / 系统提示词里绝不列举具体问题或具体答案**。客服面对的是开放问题，写死等于按问题打补丁；
- 规则层只写**通用判定原则**：资料里有依据 → 直接答；资料里没有/无法确认 → 转人工；涉及承诺/退款赔付/投诉 → 转人工；
- 业务事实（价格、时间、流程、产品）只在**资料文件**里，由检索按问题动态获取；
- 模型误判「有依据却转人工」时的兜底也必须是**通用机制**（带「复核」提示重答一次），而不是给某个词加特例。

L3 沉淀（演进层）
   对话复盘 → 候选话术/候选规则 → 人工评审 → 写入 L2 或补充 L1 → 记 changelog
```

原则：**L1 定边界和策略，L2 给事实，L0 兜底**；AI 永远不直接改写 L1（只能产出候选，等人确认）。

## 5. 关键设计问题（需要先定，决定工作量）

### 5.1 工具调用：三条路线

- **A. 声明式预取（推荐 v1）**：AGENTS.md 声明「什么场景需要什么数据」，适配器/运行时在回复前预取（店铺、订单状态、库存）拼进上下文。无工具调用风险，改动小，实时性够用。
- **B. 只读工具 function-calling（推荐 v2）**：给自动回复循环加「模型可请求 1–2 次只读工具调用」的能力（查订单、查店铺、查产品），结果回灌后生成回复。体验最好，但要处理循环/超时/幻觉调用。
- **C. 转 Agent 会话**：把买家消息交给 DSH agent（带工具 + AGENTS.md），由 agent 回复。能力最强，但时延/成本/可控性都变差，客服场景不建议。

**建议**：v1 用 A；等规则稳定再上 B 的只读白名单（写操作永远人工）。

### 5.2 产品 Excel 的接入方式

| 方案 | 做法 | 优缺点 |
|---|---|---|
| **1（推荐）导入为资料** | 上传 xlsx → 后台用 openpyxl 转成 `产品/产品表.md`（表格）+ 保留原文件 → 索引检索 | AI 能直接读；源表更新后重新导入；不需要工具调用 |
| 2 保留 xlsx + 查询工具 | 新增 `cs_product_query` 读表按型号/别名查 | 表格大时更准，但需要工具调用（依赖 5.1-B） |
| 3 以平台为准 | 产品信息以闲鱼产品库/商品详情为准，Excel 仅运营参考 | 实时性最好，但 AI 问「卖点」时不如资料表全 |

需要确认：产品表有哪些列？**成本价/供应商**这类敏感列绝对不能给买家（导入时可配置「买家可见列」白名单）。

### 5.3 图片：AI 能不能自动发

- 现状：`adapter.sendImage` 已有，但 AI 回复链路只发文本。
- 若要自动发图：回复结构里支持 `[[img:素材/xxx.png]]` → runtime 发文本后补发图片（失败降级为文字）；
- 需要素材清单（文件、用途、触发条件、是否允许自动发、是否涉及肖像/版权）；
- 建议 v1 先在 AGENTS.md 声明「哪些图可自动发」，实现发图；不确定的图一律转人工。

### 5.4 话术沉淀怎么接规则

- 现状 playbook 写旧的 `knowledge/*.md`，且无评审 → 改为：按项目沉淀 → 产出**候选变更**（新话术/FAQ 条目/规则补充建议）→ 面板「待审变更」→ 人工通过后写 L2，并在 AGENTS.md changelog 记一条；
- AI 永不直接改 AGENTS.md；
- 频率/开关/审批人需要定（建议默认关，手动「复盘一次」+ 每周自动一次）。

### 5.5 规则更新权限与流程

- 谁能改 AGENTS.md：只有你？还是运营也能改（留 changelog）？
- 改完是否立即生效（当前知识库 60s 缓存；规则可以强制立即重载）；
- 是否需要「发布前预览」：改完用自测问句跑一遍「AI 会读到什么」再保存生效。

## 9. 运营者已确认的决策（2026-10-20）

| # | 决策 |
|---|---|
| 1 | **每个项目一份 AGENTS.md**（示例店铺、高报完全独立），不做统一大模板 |
| 2 | 工具调用走 **B：只读工具调用**（像 DSH agent 一样有工具，但**只读**）；**写操作（退款/改价/关单/发品）绝不注册给 AI、绝不自动执行**，只能人工。本条要求代码层强制：白名单 + 参数校验 + 只读接口，不靠 prompt 自觉 |
| 3 | 产品 Excel：**导入成 `产品/产品表.md` 表格**（保留源 xlsx），让 AI 能检索调用；敏感列（成本价/供应商）导入时剔除 |
| 4 | **要 AI 自动发图**：在 AGENTS.md 的「素材清单」里声明图片 + 用途 + 触发条件 + 是否允许自动发 |
| 5 | 话术沉淀：**不人工审，直接入库**；**每 3 天复盘一次**，由 AI 自动填充；后期再开子 agent 做校对 |
| 6 | 规则编辑：**运营者 + 我（助手）都能改**，每次改动必须记 changelog（版本/日期/原因） |
| 7 | 每个项目自己的规则文档，不抽通用大模板 |
| 8 | 验收：**历史对话回放对比**（用真实历史消息跑新规则，对比 AI 回复与人工回复/旧回复） |

### 关于「工具调用不能直接执行、防止远程操作电脑」的承诺

客服 AI 的工具**只会在插件进程内调用白名单里的只读通道**（mtop 查询/库里检索/素材读取），
不执行 shell、不调本机命令、不装包、不读写项目外文件；
写接口在注册层就被排除（AI 拿不到 → 即使模型被诱导也无法调用），不依赖提示词约束。
